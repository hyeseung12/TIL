# 7.3 브로커 설정 (p186)

## 7.3.1 복제 팩터

- `--replication-factor` : 수동으로 토픽을 생성할 때 몇 개의 레플리카를 복제할지 개수
- `default.replication.factor` : 자동으로 생성되는 토픽들에 적용되는 default 복제 개수 (브로커에서 자동으로 토픽을 만들 때에 따른 단위 설정)
  - default: 카프카 버전 3.1 기준으로 1개

<br>

- 복제 팩터가 N이면 N-1 (한개빼고)의 브로커가 중단되더라도 토픽의 데이터를 읽거나 쓸 수 있다. -> 복제 팩터가 클수록 가용성과 신뢰성은 늘어나고 장애 발생률 줄어든다.
- 반대로 N개가 필요하다는 것은 -> 서로 다른 브로커 N개에 복제되어야 하기 때문에, 최소한 N개의 브로커가 필요함 + N개의 복사본을 저장해야해서 -> N 배의 디스크 공간이 필요하다.

<br>

- 토픽에 몇 개의 레플리카가 적절한지 고려하는 핵심 고려 사항
  - **가용성**
    - 레플리카가 하나뿐인 파티션은 정기적으로 브로커 재시작해도 작동 불능에 빠진다. 레플리카 수가 더 많을수록 가용성이 늘어남.
  - **지속성**
    - 각 레플리카는 파티션 안의 모든 데이터 복사본인데, 만약 파티션에 레플리카가 하나뿐이고 디스크 사용 불가능하게 되면 -> 모든 데이터는 유실된다.
    - 따라서, 서로 다른 저장 장치에 복사본이 더 많을수록 모든 데이터가 유실될 가능성이 줄어든다.
  - **처리량**
    - 레플리카가 추가될 때마다 브로커간 트래픽 역시 늘어난다.
      - 클러스터의 크기와 용량을 선정할 때는 이에 대한 트래픽을 고려할 필요가 있다.
        - ex. 특정 파티션에 10Mbps 속도 쓴다면 -> 하나씩 늘어날 때마다 10Mbps 속도가 느려짐.
  - **종단 지연**
    - 쓰여진 메시지를 컨슈머가 읽을 수 있다면 모든 ISR에 복제되어야 한다.
      - 레플리카 수가 더 많을수록 이들 중 하나가 느려져 -> 컨슈머도 느려진다. (특정한 브로커가 느려지면 해당 브로커를 사용하는 모든 클라이언트도 복제 팩터에 무관하게 느려짐.)
  - **비용**
    - 더 많은 레플리카를 가질수록 저장소와 네트워크에 들어가는 비용 증가한다.

<br>

- 같은 파티션의 레플리카들을 서로 다른 브로커에 저장하는데 -> 이 뿐만 아니라, 서로 다른 랙에 배치 후, 랙 이름을 잡아 줄 것을 권장한다.
- 랙 단위 사고를 방지하기 위해 브로커들은 서로 다른 랙에 배치한 뒤 `broker.rack` 브로커 설정 매개변수에 랙 이름을 잡아 줄 것을 권장.
  - 카프카는 파티션의 레플리카들이 서로 다른 랙에 분산되어 저장되도록 함으로써 가용성을 높인다.

<br>

## 7.3.2 언클린 리더 선출

- `unclean.leader.election.enable` : 이 설정은 브로커 단위(실제로는 클러스터 단위)에서만 사용 가능
  - default : false
  - Out-Of-Sync 레플리카는 리더가 될 수 없도록 되어 있다.
  - 수동으로 복구될 때까지 사용이 불가능한 상태로 남는다.
  - true로 바꾸면 파티션을 사용 가능한 상태로 만들고, 데이터 유실은 감수해야 한다.
    - true 로 바꾸어도, 클러스터가 복구되면 false로 돌리는 것을 잊지 말아야 한다.

<br>

- 필요한 상황 : 작동 불능에 빠진 리더 외에 ISR가 없으면?
  - 파티션 3개의 레플리카 중 팔로워 2개가 작동 불능에 빠졌다면 -> 해당 파티션의 유일한 사용 가능한 레플리카가 Out-Of-Sync 레플리카가 된다.
  - 이번에는 팔로워 2개가 복제 작업이 뒤쳐졌다고 가정하면 -> 복제 작업은 계속되지만, In-Sync 상태는 아니다. 리더 레플리카는 유일한 ISR로서 계속 메시지를 받는데 -> 리더도 작동 불능에 빠지면, 리더가 될 수 있는 레플리카는 Out-Of-Sync 레플리카밖에 없다.

- 결정
  - 예전 리더가 복구될 때까지 해당 파티션은 오프라인 상태가 된다. -> 몇 시간이 걸릴 수도 있다.
  - Out-Of-Sync Replica 가 새 리더가 될 수 있도록 한다면, 새 리더가 동기화를 못 한 사이 예전 리더에 쓰여졌던 모든 메시지들이 유실되고 & 컨슈머 입장에서 일관성도 어느 정도 깨진다.

<br>

## 7.3.3 최소 인-싱크 레플리카

- `min.insync.replicas` : 메시지를 '커밋(ack)'하기 위해 반드시 동기화돼 있어야 하는 레플리카의 최소 개수를 지정하는 설정입니다.
  - default : 카프카 버전 3.1 기준으로 2개

- 최소 개수보다 더 많이 작동 불능에 빠지면 -> 브로커는 더 이상 쓰기 요청을 받을 수 없고, 데이터를 전송하고자 시도하는 프로듀서는 NotEnoughReplicasException 을 받게 된다.
  - 컨슈머는 계속 존재하는 메시지 읽을 수 있다.

<br>

## 7.3.4 레프리카를 인-싱크 상태로 유지하기

- `zookeeper.session.timeout.ms` : 카프카 브로커가 주키퍼로 하트비트 전송을 멈출 수 있는 최대 시간
  - 이 간격 안에만 하트비트를 보내면 주키퍼는 브로커가 죽었다고 판단하지 않아, 제외하지도 안흔ㄴ다.
  - 버전 2.5.0 부터 6초 -> 18초로 증가
  - 일반적으로 무작위적인 변동에 영향을 받지 않을 만큼 높게, 실제로 작동이 멈춘 브로커가 적시에 탐지 될 수 있는 낮게 설정할 필요가 있다.

- `replica.lag.time.max.ms` : 해당 시간보다 오랫동안 리더로부터 데이터를 읽어오지 못하거나, 리더에 쓰여진 최신 메시지를 따라잡지 못하면 -> Out-Of-Sync 상태가 된다.
  - 2.5.0에서 10초 -> 30초로 조정되었다.
  - 컨슈머의 최대 지연에도 영향을 준다. (컨슈머가 이 메시지를 읽을 수 있게 되는 데 최대 30초가 걸릴 수 있다.)

<br>

## 7.3.5 디스크에 저장하기

- 각각 데이터의 복제본을 가지고 있는, 서로 다른 랙이나 가용 영역에 위치한 세 대의 장비가 -> 리더의 디스크에 메시지를 쓰는 것보다 더 안전하는 판단이 있어,
  - 카프카는 세그먼트를 교체할 때(기본값: 1GB)와 재시작 지전에만 메시지를 디스크에 플러시하며, 그 외의 경우에는 리눅스의 페이지 캐시 기능에 의존한다 (페이지 캐시 공간이 다 찼을 경우에만 디스크에 플러시 한다.)
  - 디스크에 더 자주 메시지를 저장하도록 설정도 가능함.
    - `flush.messages` : 메시지의 개수에 따라 싱크를 수행하게 됨. ex. 5개의 메시지를 쓰면 -> 한 번 sync
    - `flush.ms` : 얼마나 자주 메시지를 저장하는지 시간 간격 조절 ex. 1초마다 한번 sync
