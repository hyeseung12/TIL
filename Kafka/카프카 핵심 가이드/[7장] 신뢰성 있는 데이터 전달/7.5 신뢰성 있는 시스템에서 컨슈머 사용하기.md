# 7.5 신뢰성 있는 시스템에서 컨슈머 사용하기 (p195)

- 컨슈머는 카프카에 커밋된 데이터만 읽을 수 있다 (ISR에 모두 쓰여진 다음부터 가능하다.)
- 컨슈머가 하는 일은 메시지를 어디까지 읽었고, 어디까지는 읽지 않았는지를 추적하는 것이다. (누락되지 않게 필수적으로 해야함)
  - 컨슈머는 배치 단위로 읽어오고, 배치별로 마지막 오프셋을 확인 한 뒤 -> 마지막 오프셋 값에서 시작하는 다른 메시지 배치를 요청한다.

- 이전 컨슈머가 정지하기 전에 마지막으로 읽은 오프셋이 무엇인지 알아야 할 필요가 있다.

<br>

## 7.5.1 신뢰성 있는 처리를 위해 중요한 컨슈머 설정

1. `group.id` : 같은 그룹 ID를 갖는 두 개의 컨슈머가 같은 토픽을 구독하면 -> 다른 부분집합이 할당되어, 각각의 부분만의 메시지를 읽게 된다.
2. `auto.offset.reset` : 커밋된 오프셋이 없거나, 컨슈머가 브로커에 없는 오프셋을 요청할 때 -> 컨슈머가 어떻게 해야 할지를 결정한다.
  - 'earliest' : 파티션의 맨 앞에서부터 읽기를 시작
    - 중복은 가능하지만, 유실은 최소화
  - 'latest'  : 끝에서부터 읽기를 시작
    - 중복은 최소화지만, 유실은 거의 확실
3. `enable.auto.commit` : 일정한 시간에 맞춰 컨슈머가 알아서 오프셋을 커밋하는지, or 코드에서 오프셋을 커밋할지?
  - 자동으로 하면 애플리케이션에서 실수하는 사태가 발생하지 않도록 보장
  - 메시지 중복 처리를 우리가 제어할 수 없다.
  - 아직 자동 커밋이 되지 않을 상태에서 일부의 메시지를 처리한 경우 -> 메시지 중복 가능
4. `auto.commit.interval.ms` : 오프셋을 자동으로 커밋하는 경우 -> 커밋되는 주기를 설정가능
  - default : 5초

<br>

## 7.5.2 컨슈머에서 명시적으로 오프셋 커밋하기

 
1. 메시지 처리 먼저, 오프셋 커밋은 나중에
   - 폴링 루프에서 모든 처리를 하고 -> 자동 오프셋 커밋 설정 or 폴링 루프 끝에서 오프셋 커밋 or 루프 안에서 일정한 주기로 오프셋을 커밋
2. 커밋 빈도는 성능과 크래시 발생시 중복 개수 사이의 트레이드오프이다.
   - 커밋 작업은 상당한 성능 오베허드를 수반한다.
   - 커밋 주기는 성능과 중복 발생의 요구 조건 사이에서 균형을 맞추어야 한다.
3. 정확한 시점에 정확한 오프셋을 커밋하자
  - 마지막으로 처리된 메시지의 오프셋이 아닌, 마지막으로 읽어 온 메시지의 오프셋으로 처리할 경우 -> 읽기는 했지만 처리되지는 않은 메시지의 오프셋을 커밋할 수 있다.
4. 리밸런스
5. 컨슈머는 재시도를 해야 할 수도 있다
  - poll()을 호출하고, 재시도해야할 수도 있다.
    - 마지막으로 처리에 성공한 레코드에 오프셋을 기록하는 방법 1
      - 나중에 처리해야하는 레코드들을 버퍼에 저장하고, 레코드 처리를 계속한다.
    - 별도의 토픽에 쓴 뒤 계속 진행한다.
6. 컨슈머가 상태를 유지해야 할 수도 있다
  - 애플리케이션에 따라 poll() 메서드 호출 간 상태를 유지해야 할수도 있다.
    - 예를 들어 이동 평균을 계산해야한다면 -> 누적된 값을 업데이트 해야하고, 프로세스 재시작 시, 단순히 마지막 값을 읽어 오지 않고 이동 평균값 역시 복구시켜야 한다.
  - 해당 문제 해결 방법은 -> 누적된 값을 'results' 토픽에 따로 쓰는 것이다.
