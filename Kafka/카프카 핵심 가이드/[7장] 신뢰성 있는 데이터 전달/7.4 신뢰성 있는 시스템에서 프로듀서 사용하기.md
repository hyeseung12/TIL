# 7.4 신뢰성 있는 시스템에서 프로듀서 사용하기 (p192)

- unclean 리더 선출 기능을 끄면 -> 카프카 클러스터에 커밋된 메시지는 유실되지 않는다.
  - 하지만, acks = 1으로 설정한 경우, ISR에 반영안된 상태에서 리더가 프로듀서에게 '메시지가 성공적으로 쓰여졌다' 로 응답을 보내기 때문에 -> 직후 크래시가 나면 레플리카로 복제되지 않아 유실될 수 있다. (애플리케이션 입장에서는 성공으로 착각 가능)
  - acks = 'all'으로 뒤늦게 수정해도 재시도도 하지 않을 경우, 메시지는 유실될 수 있다.
  - 이것은 브로커의 신뢰성 문제와 별개의 문제다. 프로듀서가 이 에러를 정확히 처리해주지 않을 경우, 메시지 유실을 초래할 수 있다.

- 신경써야 할 중요한 두개
  - 신뢰성 요구 조건에 맞는 올바른 acks 설정을 사용한다.
  - 설정과 코드 모두에서 에러를 올바르게 처리한다.

<br>

## 7.4.1 응답 보내기

- acks = 0
  - 네트워크로 메시지를 전송한 시점에서 성공으로 간주한다.
  -파티션이 오프라인이거나, 리더 선출이 진행중이거나, 전체 카프카 클러스터가 작동 불능이어도 -> 네트워크가 오작동하지 않아, 에러가 발생하지 않을 것이다.
  - 종단 지연도 발생 가능하다. -> 컨슈머는 메시지가 모든 ISR로 복제되지 않으면 메시지를 볼 수 없기 떄문이다.
- acks = 1
  - 리더가 메시지를 받아서, 데이터 파일에 쓴 직후 응답 또는 에러를 보낸다.
    - 팔로워에 복제가 완료되기 전에 -> 리더가 정지하거나 크리쉬 난 경우 데이터 유실이 가능하다. (불완전 복제 파티션이 발생할 수 있음.)
- acks = all
  - 리더가 모든 ISR에 메시지 받을 때까지 기다렸다가 응답하거나 에러를 보낸다.
    - 가장 안전한 옵션이며, 완전히 커밋될 때까지 계속해서 메시지를 전송한다.
    - 지연이 가장 길어지는 옵션이기도 하다.

<br>

## 7.4.2 프로듀서 재시도 설정하기

- 프로듀서 에러 처리
  - 프로듀서가 자동으로 처리해주는 에러
  - 프로듀서 라이브러리를 사용하는 개발자가 처리해야 하는 에러

- 프로듀서는 재시도 가능한 에러를 처리 가능함
  - 브로커가 `LEADER_NOT_AVAILABLE` 을 보내면 -> 새로운 브로커가 리더로 선출된 상황에서 재시도할 수도 있기 때문에 재시도 한다.
  - 반대로 `INVALID_CONFIG` 와 같이 설정이 수정 필요하면 재시도 불가능한 에러이다.

<br>

- 메시지가 유실되지 않는 것이 목표이라면 -> 재시도 가능한 에러가 발생했을 경우 프로듀서가 계속해서 메시지 전송을 재시도 하는 것이다.
  - 가장 좋은 방법은 : 재시도 수를 기본값 (MAX_INT) 로 두고, 메시지 전송을 포기할 때까지 대기할 수 있는 시간을 지정하는 `delivery.timeout.ms` 을 최대로 잡아 주는 것이다.
  - 시간 간격 내에서 메시지 전송을 계속 재시도 하는 것이다.

- 재시도 후 모두 성공적으로 쓰이면, 메시지가 중복될 위험을 내포한다.
  - '최소 한 번'은 보장하지만 -> '정확히 한 번'은 보장할 수 없기 때문에
  - `enable.idempotence=true` 설정으로 중복된 메시지를 건너뛸 수 있도록 할 수 있다.

<br>

## 7.4.3 추가적인 에러 처리

- 메시지 크기에 관련되었거나 인가 관련 에러와 같이 재시도가 불가능한 브로커 에러
- 메시지가 브로커에 전송되기 전에 발생한 에러 ex. 직렬화 에러
- 프로듀서가 모든 재전송 시도를 소진했거나, 가용 메모리가 가득 차서 발생한 에러
- 타임아웃

- 아키텍처와 제품의 요구 조건에 따라 달라지는 에러 처리이다.
