# 6.2 컨트롤러 (p150)

- 클러스터에서 가장 먼저 시작되는 브로커는 주키퍼의 `/controller` 에 Ephemeral 노드를 생성한다.

- 다른 브로커 역시 시작할 때 이를 생성하려고 시도하지만 활성 컨트롤러는 하나이기 떄문에 '이미 존재함' 예외를 받아 이미 컨트롤러가 존재하는 걸 알아차린다.

- 컨트롤러 브로커가 멈추거나, 연결이 끊기면 -> 노드도 삭제된다.
  - `zookeeper.session.timeout.ms`에 설정된 값보다 더 오랫동안 주키퍼에 하트비트 전송하지 않으면 이 상황도 노드가 삭제된다.
  - 다른 브로커는 해당 컨트롤러 브로커가 삭제되는 것을 알고 컨트롤러 생성을 시도한다.
    - 가장 먼저 생성 성공한 브로커가 그 다음 컨트롤러가 된다.

- 에포크는 컨트롤러가 교체될 때마다 1씩 증가하는 값으로, `현재 컨트롤러가 몇 세대 리더`인지 나타내는 값인데, 해당 값으로 이전의 에포크 값을 가진 컨트롤러로부터 메시지를 받으면 무시한다.
  - 이전 컨트롤러가 작업을 재개할 경우, 새로운 컨트롤러가 선출된 것도 모르고 브로커에 메시지를 보낼 가능성이 있어 이를 무시하는 것이다.
  - 이러한 컨트롤러를 '좀비' 라고 부른다.
  - Split brain 현상은 2개 이상의 컨트롤러가 생기는 현상으로, 따라서 이를 방지하기 위해 에포크 번호가 사용된다.

- 브로커가 클러스터를 나갔다는 사실을 컨트롤러가 알아차리면, 다음과 같은 행동을 한다.
  - 해당 브로커가 리더를 맡고 있었던 모든 파티션에 대해 새로운 브로커를 할당해준다.
  - 새로운 리더가 필요한 모든 파티션을 순회해 가며 새로운 리더가 될 브로커를 결정한다.
    - 단순히 해당 파티션의 레플리카 목록에서 바로 다음 레플리카가 새 브로커가 된다.
  - 새로운 상태를 주키퍼에 쓴다. (비동기 방식으로 여러 개로 나누어 보낸다.)
  - 새로 리더가 할당된 파티션의 레플리카를 포함하는 모든 브로커에 `LeaderAndISR` 요청을 보낸다.
    - 이 요청은 파티션에 대한 새로운 리더와 팔로워 정보를 포함한다.
    - 효츌성을 위해 이러한 요청은 배치 단위로 묶여 전송된다.

- 새로 리더가 된 브로커 각각은 클라이언트로부터 쓰기 혹은 읽기 요청을 처리하기 시작한다. 반면 팔로워들은 새 리더로부터 메시지를 복제하기 시작한다.

- 클러스터 내 모든 브로커는 전체 브로커와 레플리카의 맵을 포함하는 `MetadataCache`를 가지고 있어 -> 컨트롤러는 모든 브로커에 리더십 변경 정보를 포함하는 `UpdateMetadata` 요청으로 캐시를 업데이트 하도록 한다.

## 6.2.1 KRaft: 카프카의 새로운 래프트 기반 컨트롤러

- 카프카 버전 3.3 이상부터 프로덕션 환경이 완성되었다.

주키퍼의 단점은

1. 컨트롤러가 주키퍼에 메타데이터 쓰는 건 동기인데, 브로커 메시지를 보내거나 주키퍼로부터 업데이트를 받는 과정은 비동기이다. -> 이에 대한 데이터 불일치 및 잡아내기도 어렵다.

2. 컨트롤러가 재시작되면 주키퍼에 모든 브로커와 파티션에 대한 메타데이터를 읽고, 모든 브로커에 전송된다.
   -> 파티션 & 브로커 수 증가에 따라 컨트롤러 재시작에 지연이 된다.

3. 메타데이터 소유권이 좋지 못하다. (컨트롤러, 브로커, 주키퍼..)

4. 주키퍼도 분산 시스템이라, 개발자에게 학습을 요구한다.

주키퍼의 주요 역할은 다음과 같다.

1. 컨트롤러 선출
2. 클러스터 메타데이터 저장 (즉, 현재 운영중인 브로커, 설정, 토픽, 파티션 그리고 레플리카 관련 정보에 대한 저장)

새로운 컨트롤러의 핵심 아이디어

- 카프카 그 자체에 사용자 상태를 이벤트 스트림으로 나타낼 수 있도록 하는 로그 기반 아키텍처 도입한다.
-> 최신 상태를 빠르게 잡을 수 있고, 이벤트 순서 부여로 컨슈머들이 항상 하나의 타임라인으로 움직임을 보장한다.

- 새로운 아키텍처에서 컨트롤러 노드들은 메타데이터 이벤트 로그를 관리하는 래프트 쿼럼이 된다.
  - 이 로그는 클러스터 메타데이터의 변경 내역을 저장한다.
  - 현재 주키퍼에 저장되어 있는 모든 정보들 (토픽, 파티션, ISR, 설정 등등) 여기에 저장

- 래프트 알고리즘으로 -> 컨트롤러 노드들은 외부 시스템에 의존하지 않고 자체적으로 리더를 선출할 수 있게 될 것이다.

- 액티브 컨트롤러는 브로커가 보내온 모든 RPC 호출을 처리한다.
  - RPC 란? 다른 서버(원격)에 있는 함수를 호출하는 통신 방식이다. 
  - ex. UpdateMetadataRequest, LeaderAndISRRequest
  - 팔로워 컨트롤러들은 액티브 컨트롤러에 쓰여진 데이터들을 복제한다. -> 장애 발생 시, 바로 투입될 수 있도록 (reload period를 필요로 하지 않는다.)

- 컨트롤러는 Push하지 않고 브로커가 pull 한다.
  - -> 강제로 '파티션 위치 바뀌었어' 를 보내지 않고, 브로커가 '최신 정보 있어?'를 요청하는 방식

- 브로커 프로세스는 시작 시 주키퍼가 아닌, 컨트롤러 쿼럼에 등록하고 -> 운영자가 등록 해제하지 않는 한 이를 유지한다.
  - 최신 상태를 유지하지는 않은 브로커의 경우 fenced 된 상태로 클라이언트 요청을 처리할 수 없다.

## 컨트롤러? 어느 컨트롤러?

KRaft 도입 이후 용어 정리

- KRaft 도입 이전 프로세스
  - 주키퍼 프로세스 : 카프카 클러스터의 동적 메타데이터를 저장하는 역할
  - 카프카 프로세스 : 카프카 데이터를 저장하는 역할 -> 이들 중 리더 파티션을 결정하는 역할을 하는 프로세스를 컨트롤러라고 한다.
  - '브로커'는 '카프카 프로세스'와 동의어
  - '컨트롤러'는 브로커 중에서 파티션 리더를 결정하는 역할을 맡는 어느 특별한 브로커

- KRaft 이후 주키퍼 프로세스는 삭제
  - 카프카 프로세스가 다음의 두 개중 하나의 역할 또는 두 역할을 겸하게 되었다.
    - 컨트롤러 : 카프카 클러스터의 동적 메타데이터를 저장하는 역할을 한다.
    - 브로커 : 카르카 데이터를 저장하는 역할을 한다.
  - '브로커'는 카프카 프로세스가 맡을 수 있는 특정한 '역할'
  - '컨트롤러'는 동적 메타데이터를 저장하는 역할을 하는 카프카 프로세스를 가리킨다.

## 어떻게 KRaft로 옮겨갈 수 있을까?

- 기존에 주키퍼에 저장된 메타데이터를 컨트롤러 쿼럼으로 이전시킬 수 있도록 '브리지 릴리스'를 제공할 예정. (버전 3.4 에서 액세스 기능으로서 막 탑재된 상태.)
