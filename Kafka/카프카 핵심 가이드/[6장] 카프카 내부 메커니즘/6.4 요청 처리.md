# 요청 처리 (p161)

- 카프카는 TCP로 전달되는 이진 프로토콜을 가지고 있다.
- 모든 요청은 다음의 표준 헤더를 갖는다.
  - 요청 유형 : API 키라고도 불린다.
  - 요청 버전 : 브로커는 서로 다른 버전의 클라이언트로부터 요청을 받아 각각의 버전에 맞는 응답을 할 수 있다.
  - Correlation ID : 각각의 요청에 붙는 고유한 식별자.
  - 클라이언트 ID : 요청을 보낸 애플리케이션을 식별

- 브로커는 연결을 받는 각 포트별로 억셉터 스레드를 하나씩 실행시킨다.
  - 억셉트 스레드는 연결을 생성하고 들어온 요청을 프로세서 스레드에 넘겨 처리하도록 한다.
- 프로세서 스레드의 수는 설정 가능하다. 네트워크 스레드는 클라이언트 연결로부터 들어온 요청을 큐로 넣고, 응답 큐에서 응답을 가져다 클라이언트로 보낸다.
- 컨슈머의 경우 브로커 쪽에 데이터가 준비되었을 때에만 응답을 보낼 수 있고, 어드민 클라이언트도 토픽 삭제가 진행중인 상황에서만 요청에 대한 응답을 보낼 수 있다.

<br>

클라이언트 요청 유형

1. 쓰기 요청
  - 카프카 브로커로 메시지를 쓰고 있는 프로듀서가 보낸 요청
  - 브로커가 다른 브로커가 리더를 맡고 있는 파티션에 대한 쓰기 요청을 받을 경우 'Not a Leader for Partition' 에러를 반환한다. (브로커가 리더를 맡고 있지 않은 파티션에 대한 읽기 요청도 동일한 에러다.)

2. 읽기 요청
  - 캬프카 브로커로부터 메시지를 읽어오고 있는 컨슈머나 팔로워 레플리카가 보낸 요청

3. 어드민 요청
  - 메타데이터 작업을 수행중인 어드민 클라이언트가 보낸 요청
    - 메타데이터 캐시 중임. (`metadata.max.age.ms`로 이 정보를 새로고침하는 간격을 조정할 수 있다.)
      - 요청에 대해 'Not a Leader' 에러를 리턴받은 경우, 요청을 재시도 하기 전에 메타데이터를 먼저 새로고침합니다.

## 6.4.1 쓰기 요청

<img src="https://img1.daumcdn.net/thumb/R1280x0/?scode=mtistory2&fname=https%3A%2F%2Fblog.kakaocdn.net%2Fdna%2FwFrLU%2FbtsjjzxJikK%2FAAAAAAAAAAAAAAAAAAAAAH6KMvmdDVVMkknaMlI7X2oUkb6JO0xSHCo7S49SXU-a%2Fimg.png%3Fcredential%3DyqXZFxpELC7KVnFOS48ylbz2pIh7yKj8%26expires%3D1761922799%26allow_ip%3D%26allow_referer%3D%26signature%3DqzlDJUajHPIHfduOfAXuq%252BxF0Ag%253D">

- 파티션에 대한 쓰기 요청을 받으면 다음의 유효성 검사를 한다.
  - 데이터를 보내는 쪽이 토픽에 대한 쓰기 요청 권한을 가지고 있는가?
  - 요청에 지정되어 있어 acks 설정값이 올바른가? (0, 1, 'all'만 사용 가능)
  - 'all'인 경우, 메시지를 안전하게 쓸 수 있을 만큼 충분한 In-Sync 레플리카가 있는가? (In-Syc 레플리카 수가 설정 값보다 아래로 내려가면, 새로운 메시지를 받지 않도록 브로커 설정 가능)

- 그러고 나서 브로커는 새 메시지들을 로컬 디스크에 쓴느데, 해당 디스크에 저장될 때까지 기다리지 않는다. -> 복제에 의존한다.

- 메시지가 파티션 리더에 쓰이고 나면, 브로커는 acks 설정에 따라 응답을 내려보낸다.
  - 0 또는 1 인 경우 : 바로 응답 보냄
  - 'all' -> 퍼거토리라는 버퍼에 저장 후, 메시지 복제한 것을 확인한 다음에야 클라이언트에 응답을 돌려보낸다.

## 6.4.2 읽기 요청

<img src="https://img1.daumcdn.net/thumb/R1280x0/?scode=mtistory2&fname=https%3A%2F%2Fblog.kakaocdn.net%2Fdna%2FbsabkQ%2FbtsjjBPOHcl%2FAAAAAAAAAAAAAAAAAAAAAHX0YMQGKdv7LNxTeAJsZ-u8-TPNhZW6xmvamivb5eSt%2Fimg.png%3Fcredential%3DyqXZFxpELC7KVnFOS48ylbz2pIh7yKj8%26expires%3D1761922799%26allow_ip%3D%26allow_referer%3D%26signature%3Drvk%252BfTygO%252B34xp774E1HOfOjX%252B4%253D">

1. 컨슈머가 브로커에 읽기 요청 했을 때, 유효한지도 브로커에서 확인한다.
   - 지정된 오프셋이 해당 파티션에 존재하는지? -> 없다면 에러를 반환한다.

2. 클라이언트는 각 파티션에 대해 브로커가 리턴할 수 있는 최대 데이터의 양을 지정한다.
   - zero-copy 최적화를 적용한다.
      - 리눅스의 파일시스템 캐시에서 읽어온 데이터를 중간 버퍼를 거치지 않고, 바로 네트워크 채널로 보낸다.
      - 장점 : 데이터를 복사하고 메모리 상 버퍼를 관리하기 위한 오버헤드가 사라지며, 결과적으로 성능 향상한다.

3. 브로커가 리턴할 수 있는 데이터 양 상한을 지정하는 것에 더해서, 하한도 정할 수 있다.
   - 클라이언트가 트래픽이 그리 많지 않은 토픽들로부터 메시지를 읽어오고 있을 때 CPU와 네트워크 사용량 감소 시킨다.
   - 장점 : 같은 양의 데이터를 읽지만, 데이터를 주고받는 횟수는 훨씬 적으므로 오버헤드도 그만큼 적다.
   - 마냥 기다리는 것은 원하지 않을 때 -> 타임아웃 역시 지정해줄 수 있다.

<br>

<img src="https://img1.daumcdn.net/thumb/R1280x0/?scode=mtistory2&fname=https%3A%2F%2Fblog.kakaocdn.net%2Fdna%2F0qiXn%2Fbtsjk5JHXzH%2FAAAAAAAAAAAAAAAAAAAAAGvSRTIDXrfhk-3fOYVHH1Wn9BLq4000wbkXxjINWDVd%2Fimg.png%3Fcredential%3DyqXZFxpELC7KVnFOS48ylbz2pIh7yKj8%26expires%3D1761922799%26allow_ip%3D%26allow_referer%3D%26signature%3DrCZobo661YBepEWodNjP6zVafhU%253D">

- 컨슈머는 모든 In-Sync Replica 에 복제된 메시지들만 읽을 수 있다.
  - 특정 메시지가 모든 In-Sync Replica에 쓰여지기 전까지 컨슈머들이 읽을 수 없다.
  - 이 메시지를 읽으면 에러가 아닌, 빈 응답으로 내려간다.
  - 이렇게 읽을 수 없는 상태의 메시지는 '불안전' 한 것으로 간주한다.
    - -> 만약 리더가 크래시가 발생할 경우, 해당 메시지는 카프카에서 유실된다.
  - 그래서 복제가 다 될 때까지 기다려야하는데 -> 이 지연시간은 `replica.lag.time.max.ms` 의해 제한된다. (이 이후 시간은 out-opf-sync replica가 된다.)

<br>

- 컨슈머가 매우 많은 수의 파티션들로부터 이벤트를 읽어오는 경우가 있다.
  - 이 경우 읽고자 하는 파티션의 전체 목록을 요청을 보낼 때마다 브로커 전송 후 다시 돌려 보내는 방식은 매우 비효율적이다.
  - 오버헤드를 최소화하기 위해 카프카는 읽기 세션 캐시를 사용한다.
     - 읽고 있는 파티션의 목록과 그 메타데이터를 캐시하는 세션을 생성할 수 있다.
     - 단, 세션 캐시는 한도가 있기 때문에, 카프카는 팔로워 레플리카나 읽고 있는 파티션의 수가 더 많은 컨슈머를 우선시 한다.
        - 어떤 경우에는 아예 생성 되지 않거나, 생성된 게 해제되거나, 적절한 에러를 보내거나, 사용자가 개입안해도 일기 요청을 보낼 것이다.
