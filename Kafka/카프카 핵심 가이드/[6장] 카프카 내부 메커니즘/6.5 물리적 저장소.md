# 물리적 저장소 (p169)

- 카프카의 기본 저장 단위 : 파티션 레플리카
- 핵심 요약
   - 파티션은 한 브로커의 한 디스크에만 저장된다.
   - 여러 브로커나 여러 디스크로 나눠 저장할 수 없다.
     - 단, JBOD 설정을 사용하면 -> 여러 디스크를 하나로 해서 하나의 마운트 지점으로 포함 가능하다.
   - 그래서 디스크 공간이 곧 파티션의 한계이다.
   - kafka 설정 파일의 log.dirs 옵션으로 데이터를 저장할 디렉토리(디스크 위치) 지정이 필요하다.

<br>

## 6.5.1 계층화된 저장소

- 카프카 3.6.0에서 신규 출시 및 3.9.0 에서 프로덕션 준비 완료로 선언했다고 한다. (공식 문서 기준)

- 사용해야 했던 상황
   - 파티션별로 저장 가능한 데이터에는 한도가 있었다.
     - 최대 보존 기한과 파티션 수는 제품의 요구 조건이 아닌 물리적인 디스크 크기에도 제한을 받는다.
   - 디스크와 클러스터 크기는 저장소 요구 조건에 의해 결정된다. -> 클러스터가 필요한 것 이상으로 커지면 비용과 직결된다.
   - 클러스터 크기를 키우거나 줄일 때 -> 다른 브로커로 파티션 위치를 옮겨야 하는데, 이는 탄력성을 줄어드게 한다.

<br>

- 카프카 클러스터의 저장소를 로컬과 원격으로 나눈다.
  - 로컬 : 로컬 디스크 사용
    - 로컬 보존 기한 : 몇 시간 이하 설정
  - 원격 : 로그 세그먼트를 저장하기 위해 HDFS나 S3 같은 시스템 사용
- 원격 보존 기한 : 며칠 ~ 몇 달로 설정

- 로컬 저장소 지연 < 원격 저장소 지연

- 로컬 저장소는 최신 데이터를 전달하며, 원격 저장소는 더 오래된 데이터를 전달한다.

- 장점 : 계층화된 저장소 기능의 이중화된 구조 덕분에 카프카 클러스터의 메모리와 CPU에 상관없이 저장소를 확장할 수 있다.
  - 카프카는 장기간용 저장 솔류션으로의 역할 가능해짐
  - 로컬에 저장되는 데이터 양 역시 줄고, 복구와 리밸런싱 과정에서 복사되어야 할 데이터 양 역시 줄어든다.
  - 원격 계층은 바로 클라이언트로 전달된다.
  - 전체 데이터 보존 기한 역시 더 길게 잡아줄 수 있다.

<br>

- 계층화된 저장소의 도입으로 인한 성능 변화
   1. 원격 저장소로 로그 세그먼트를 전송해야 하는 만큼 지연이 약간 증가함 (21ms -> 25ms)
   2. 오래된 데이터를 읽어오는 경우 (21ms~60ms -> 25ms~42ms)
   
<br>

## 6.5.2 파티션 할당

- 레플리카들은 가능한 한 브로커 간에 고르게 분산시킨다.
- 각 파티션에 대해 각각의 레플리카는 서로 다른 브로커에 배치되도록 한다.
- 만약 브로커에 랙 정보가 설정되어 있다면 -> 가능한 한 각 파티션의 레플리카들은 서로 다른 랙에 할당한다. (하나의 랙이 불능이어도 전체 사용 불능은 방지할 수 있음.)

- 새로운 파티션을 저장할 디렉토리 결정은 -> 제일 적게 파티션이 저장된 디렉토리에 추가한다. (크기가 아닌 수로만 확인한다.)

<br>

## 6.5.3 파일 관리

- 카프카 운영자가 각 토픽에 대해 보존 기한을 설정할 수 있다.
- 세그먼트는 파티션을 구성하는 실제 파일인데, 하나의 파티션이 너무 크면, 여러 개의 세그먼트로 분할한다.
  - 기본적으로, 1GB의 데이터 혹은 최근 1주일치의 데이터 중 적은 쪽만큼을 저장한다.
  - 다 차면, 새로운 세그먼트를 생성한다.
- 현재 쓰이고 있는 세그먼트를 '액티브 세그먼트' 라고 한다.
  - 어떠한 경우에도 삭제되지 않는다.

<br>

## 6.5.4 파일 형식

- 각 세그먼트는 하나의 데이터 파일 형태로 저장한다.
  - 각 메시지와 오프셋이 저장된다.
- 네트워크를 통해 전달되는 형식과 디스크에 저장되는 형식을 통일하여 -> zero-copy를 최적화할 수 있었다.
- 카프카 메시지는 사용자 payload와 시스템 header 두 부분으로 나뉜다.
  - 사용자 payload는
    - 키값(선택사항)
    - 밸류값
    -헤더 모음(선택사항)
  - 헤더는 키/밸류 순서쌍이다.
- 언제나 메시지는 배치 단위로 전송된다. (`linger.ms=10`으로 잡아줄 때, 더 성능이 좋아지는 이유이다.)

<br>

- 메시지 배치 헤더는 다음과 같은 것들이 포함된다.
  - 메시지 형식 버전 -> 매직 넘버
  - 첫 메시지 오프셋과 마지막 오프셋 차이
    - 배치에서는 0으로 하고 -> 브로커에서 실제 오프셋으로 변경한다.
  - 첫번쨈 메시지 timestamp와 배치에서 가장 큰 timestamp.
    - 유형이 생성 시각이 아닌 append time 이면 -> 브로커가 타임스탬플를 잡아주게 된다. 
  - 바이트 단위의 배치 크기
  - 리더의 에포크 값 (버전 값)
  - 배치가 오염(데이터 깨짐) 없는 지 확인하는 체크섬(검증 숫자)
  - 서로 다른 속성을 표시하기 위한 16비트 : 압축 유형, timestamp 유형, 배치가 트랜잭션의 일부 또는 컨트롤 배치인 지 여부
  - 프로듀서 ID, 프로듀서 에포크(버전), 배치의 첫 시퀀스 넘버 : '정확히 한 번' 보장을 위해 사용
  - 배치에 포함된 메시지 집합

<br>

- 메시지 각각의 헤더 정보
  - 바이트 단위로 표시된 레코드의 크기
  - 속성 : 현재로서 레코드 단위 속성은 없어 사용하지 않음
  - 현재 레코드 오프셋과 배치 내 첫 번째 레코드의 오프셋 차이
  - 현재 레코드 timestamp와 배치 내 첫 번째 레코드의 timestamp 차이 (ms)
  - 사용자 payload : 키, 밸류 그리고 헤더

<br>

## 6.5.5 인덱스

- index 파일로 세그먼트 파일을 빠르게 찾을 수 있다.
  - 오프셋 <-> 메시지
  - 오프셋 <-> timestamp 기준으로 메시지 찾을 때 사용한다.

- 메시지 삭제할 때, 오래된 인덱스 항목도 삭제할 수 있다.
- 인덱스에 체크섬을 유지하거나 하지 않는다.
  - 인덱스 오염 -> 메시지를 다시 읽어서 오프셋과 위치를 기록하는 방식으로 재생성한다.

<br>

## 6.5.6 압착

- 카프카는 두 가지 보존 정책을 허용한다.
  - 삭제 보존 정책 : 지정된 보존 기한보다 더 오래된 이벤트들을 삭제
  - 압착 보존 정책 : 토픽에서 각 키의 가장 최근값만 저장하도록 함.
    - 키 값이 null이면 압착은 실패함.
    - 예시) 고객의 배송지 주소를 저장할 때 -> 삭제 정책 적용하여 지난 1주일 동안, 혹은 1년 동안의 변경 내역의 데이터를 저장하는 것보다 -> 가장 마지막의 것만 저장하는 것이 더 합리적임
  - 둘 다 잡을 수 있다. -> 지정된 보존 기한보다 오래 된 메시지들은 키에 대한 가장 최근값인 경우에도 삭제 가능하다.

<br>

## 6.5.7 압착의 작동 원리

- 파티션 로그는 두 영역으로 나누어진다.
  - 클린(Clean)
    - 이전에 압착된 적이 있었던 메시지들이 저장됨
    - 하나의 키마다 하나의 값만 포함하고 있음 (이전 압착 작업 시점에서의 최신값들)
  - 더티(Dirty)
    - 마지막 압착 작업 이후 쓰여진 메시지들이 저장됨

- 압착 수행 여부
  - 압착 기능이 활성화되어 있는 경우 (`log.cleaner.enabled = true`)
    - 각 브로커는 압착 매니저 스레드와 함께 다수의 압착 스레드를 시작 시킴
    - 각 스레드는 전체 파티션 크기 대비 더티 메시지의 비율이 가장 높은 파티션을 골라 압착한 뒤 클린 상태로 만든다.

## 6.5.8 삭제된 이벤트

- 상황1) 특정 키를 갖는 모든 메시지를 삭제하고 싶을 때
  - 토픽의 압착 기능 사용
    - key : 삭제하고자 하는 키 값과 value : null로 메시지를 발행한다.
    - 클리너 스레드가 해당 메시지 발견하면 -> 압착 작업을 하고 메시지를 보존하게 된다.
    - 카프카는 설정된 기간동안 해당 메시지를 보존하게 된다.
    - 이 기간 동안, 컨슈머는 해당 메시지를 보고 해당 값이 삭제되었음을 알 수 있고, 보존 이후 클리너 스레드는 메시지를 삭제하고 -> 해당 키 역시 카프카 파티션에서 완전히 삭제하게 됨.

- 상황 2) 지정된 오프셋 이전의 모든 레코드를 삭제할 때
  - 카프카 어드민 클라이언트의 deleteRecords 메서드 사용
    - 카프카는 파티션의 첫 번째 레코드를 가리키는 로우 워터마크를 해당 오프셋으로 이동시킴
    - 컨슈머는 업데이트된 로우 워터마크 이전 메시지들을 읽을 수 없어 -> 접근 불가능
    - 해당 레코드들은 나중에 클리너 스레드에 의해 실제로 삭제됨

<br>

## 6.5.9 토픽은 언제 압착되는가?

- 대상
  - 삭제 정책과 마찬가지로 압착 정책 역시 -> 현재의 액티브 세그먼트는 절대 압착하지 않음
    - 액티브 세그먼트가 아닌 세그먼트에 저장되어 있는 메시지만이 압착의 대상

- 시점
  - 기본적으로, 카프카는 토픽의 50% 이상이 더티 레코드인 경우에만 압착을 시작함
  - 토픽을 자주 압착하지 않고(압착은 토픽의 읽기/쓰기 성능에 영향을 줄 수 있음), 너무 많은 더티 레코드가 존재하지 않도록 하는 것이 목표이다. (디스크 공간 낭비 줄임)

- 설정 매개변수로 압착 시점을 조절할 수 있음.
  - `min.compaction.lag.ms` : 메시지가 쓰여진 뒤 압착될 때까지 지나가야 하는 최소 시간 지정 (해당 시간 이후부터 압착 가능)
  - `max.compaction.lag.ms` : 메시지가 쓰여진 뒤 압착이 가능해질 때까지 딜레이 될 수 있는 최대 시간 지정 (특정 기한 안에 압착이 반드시 실행된다는 것을 보장해야하는 상황에 자주 사용)
