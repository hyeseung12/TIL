# 4.1 카프카 컨슈머 개념 (p83)

## 4.1.1 컨슈머와 컨슈머 그룹

**컨슈머와 컨슈머 그룹의 정의**

- 카프카 컨슈머는 보통 컨슈머 그룹의 일부로서 작동한다.
  - 각각의 컨슈머는 해당 토픽에서 서로 다른 파티션의 메시지를 받는다.
  - 하나의 컨슈머가 토픽에 들어오는 데이터의 속도 감당 못하는 경우 -> 일반적으로 컨슈머를 추가함으로써 단위 컨슈머가 처리하는 파티션과 메시지의 수를 분산시킨다.
    - 단, 토픽에 설정된 파티션 수 이상으로 컨슈머를 투입하는 것은 무의미하다.
  - 새로운 컨슈머 그룹을 추가하면, 두 그룹 모두 모든 메시지를 받는다.

<br>

## 4.1.2 컨슈머 그룹과 파티션 리밸런스

**리밸런스란?**

- 컨슈머 그룹에 속한 컨슈머들은 구독하는 토픽의 파티션들에 대한 소유권을 공유한다.
  - 컨슈머가 종료되거나, 크래시 났을 경우에도, 이전에 다른 컨슈머가 읽고 있던 파티션으로부터 메시지를 읽기 시작한다.
  - -> 이렇게 컨슈머에 할당된 파티션을 다른 컨슈머에게 할당해주는 작업을 '리밸런스(rebalance)' 라고 한다.
    - 리밸런스는 컨슈머 그룹에 쉽고 안전하게 컨슈머를 제거할 수 있도록 해줌과 동시에 높은 가용성과 규모 가변성을 제공하는 기능이다.

<br>

**조급한 리밸런스(eager rebalance)**

- 모든 컨슈머가 읽기 작업을 멈추고, 자신에게 할당된 모든 파티션의 소유권을 포기한 뒤, 컨슈머 그룹에 다시 참여하여 완전히 새로운 파티션 할당을 전달받는다.

**협력적 리밸런스(cooperative rebalance)**

1. 컨슈머 그룹 리더가 다른 컨슈머들 각자에게 할당된 파티션 중 일부가 재할당 될 것이고 통보하면 -> 데이터를 읽어오는 작업을 멈추고, 해당 파티션에 대한 소유권을 포기한다.

2. 컨슈머 그룹 리더가 위의 포기한 파티션을 새로 할당한다.

- 장점 : eager rebalance 처럼 전체 중단을 하지 않는다. (재할당되지 않은 파티션은 계속 처리할 수 있다.)

**kafka 버전에 따른 리밸런싱**

- kafka 버전 2.4 이하는 **eager rebalance** 가 default 값이었다.
- kafka 버전 2.4 ~ 3.1 미만부터 **cooperative rebalance** 가 본격적으로 지원되었지만, 여전히 default는 **eager rebalance** 이다.
- kafka 버전 3.1 이상부터 **cooperative rebalance** 가 default 값이 되었다.
- kafka 버전 4.0 부터 **eager rebalance**는 완전히 중단되었다.

<br>

**컨슈머 그룹 코디네이터(consumer group coordinator)**

- 코디네이터 역할을 지정받은 카프카 브로커의 역할 중 하나는 -> 컨슈머들의 하트비트(HEARTBEAT)를 수신하여 각 컨슈머의 Running 상태를 확인합니다.
   - 하트비트는 컨슈머의 백그라운드 스레드에 의해 전송되며, 일정한 간격을 두고 전송되는 한 연결이 유지되는 것으로 간주합니다.
   - 브로커 하나는 코디네이터 역할을 동시에 처리할 수도, 따로 처리할 수도 있습니다.
   
- 만약 일정 시간 동안 하트비트를 전송하지 않는다면, 세션 타임아웃이 발생하면서 해당 컨슈머가 죽었다고 간주하고 리밸런스를 실행합니다.
   - 여기서 정상적으로 consumer가 종료된 것이라면 -> 바로 리밸런스를 실행시키고,
   - 비정상적으로 (크래시 등의 이유로) 종료된 경우 -> 세션 타임아웃을 기다렸다가 리밸런스를 합니다.

<br>

**파티션은 어떻게 컨슈머에게 할당되는가?** 

<br>
1. JoinGroup 요청: 그룹에 참여 요청

  - 각 컨슈머는 Kafka 브로커 중 하나에 **Group Coordinator**로 지정된 브로커에게 `JoinGroup` 요청을 보냅니다.
  - 컨슈머가 처음 그룹에 참여하거나, 리밸런스가 필요한 상황일 때 이 요청이 발생합니다.

<br>
2. 그룹 리더 선정

  - 가장 먼저 `JoinGroup` 요청을 보낸 컨슈머가 **그룹 리더 (Group Leader)** 로 선출됩니다.
  - 리더는 이후 파티션 할당을 책임지게 됩니다.

<br>
3. 구성원 목록 수신

  - 그룹 코디네이터는 리더에게 현재 그룹에 포함된 **"모든 살아 있는 컨슈머 목록"** 을 전달합니다.
    - 이 목록은 최근 하트비트(heartbeat)를 통해 활성 상태로 간주된 컨슈머들만 포함됩니다.

<br>
4. 파티션 할당 수행

  - 그룹 리더는 전달받은 컨슈머 목록과 구독한 토픽의 파티션 정보를 바탕으로,
  **`PartitionAssignor` 인터페이스의 구현체**를 사용하여 파티션을 각 컨슈머에게 분배합니다.
    - Kafka 기본 내장 정책: `RangeAssignor`, `RoundRobinAssignor`, `StickyAssignor` 등.
    - 카프카 버전 3.0 부터는 해당 인터페이스는 삭제되었고, `org.apache.kafka.clients.consumer.ConsumerPartitionAssignor` 을 사용함으로 명시되어 있음.
    - https://kafka.apache.org/31/documentation.html#upgrade_300_notable

<br>
5. 할당 내역 전달

  - 파티션 할당이 완료되면, 그룹 리더는 할당 결과를 그룹 코디네이터에게 전달합니다.
  - 그룹 코디네이터는 이를 다시 각 컨슈머에게 전파합니다.
    - 각 컨슈머는 오직 자신에게 할당된 파티션 정보만 수신합니다.  
    - 그룹 리더만 전체 파티션 할당 내역을 확인할 수 있습니다.

<br>
6. 리밸런스 반복

- 토픽 변경, 컨슈머 추가/제거, 세션 타임아웃 등으로 인해 리밸런스가 발생하면, 위 과정이 반복됩니다.

<br>

```plaintext
[Consumer] --JoinGroup--> [Group Coordinator]

[Group Coordinator] --select leader--> [Leader Consumer]
[Group Coordinator] --send member list--> [Leader Consumer]

[Leader Consumer] --partition assignment (using PartitionAssignor)--> (internal)
[Leader Consumer] --send assignment--> [Group Coordinator]

[Group Coordinator] --send assignments--> [All Consumers]
```

<br>

## 4.1.3 정적 그룹 멤버십

- 기본적으로, 컨슈머가 갖는 컨슈머 그룹의 멤버로서의 자격(멤버십)은 일시적이다.
  - 컨슈머가 그룹 떠나면 -> 해제되고, 다시 들어와도 -> rebalance에 의해 새로운 파티션에 할당된다.

- 하지만 컨슈머에 고유한 `group.instance.id` 를 할당하면 -> 예전에 할당된 파티션을 그대로 재할당한다.
  - 정적 멤버는 종료할 때 자동으로 그룹을 떠나지 않는다 -> `session.timeout.ms` 설정의 값이 지나야 그룹의 멤버에서 떠난다.
     - 이 session.timeout.ms 값은 `애플리케이션 재시작 시간 < 값 < 파티션 처리 중단 허용 시간`으로 설정할 필요가 있다.
  - 그룹 코디네이터는 파티션 할당을 캐시해두고 있기 때문에 rebalance를 하지 않는 것이다.
     - 만약, 정지되었던 컨슈머가 다시 돌아오면, 이 파티션에 저장된 최신 메시지에서 한참 뒤에 밀린 메시지부터 처리하게 된다.
       - 따라서, 해당 컨슈머가 재시작했을 때 밀린 메시지들을 따라잡을 수 있을지 확인할 필요가 있다.
  - 만약 같은 ID로 동일한 그룹에 조인하면, 두번쨰 컨슈머에는 동일한 ID가 존재한다고 에러가 발생하게 될 것이다.
