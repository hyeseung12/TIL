# 4.4 폴링 루프 (p92)

- 컨슈머 API의 핵심은 서버에 추가 데이터가 들어왔는지 폴링하는 루프다.
- 폴링 루프는 단순히 데이터를 가져오는 것보다 훨씬 더 많은 일을 한다.
  - 새 컨슈머에서 처음으로 poll()을 호출하면 컨슈머는 GroupCoordinator를 찾아서 컨슈머 그룹에 참가하고 ,파티션을 할당받는다.
  - 리밸런스 역시 연관된 콜백들과 함께 여기서 처리된다. 
  - -> 컨슈머 혹은 콜백을 모두 호출되기 때문에, 이에 뭔가 잘못 될 수 있는 거의 모든 것들은 poll()에서 예외의 형태로 발생되는 것이다.

- poll()이 `max.poll.interval.ms`에 지정된 시간 이상으로 호출되지 않은 경우 -> 컨슈머가 죽은 것으로 판정되어 컨슈머 그룹에서 퇴출된다.

## 4.4.1 스레드 안정성

**컨슈머와 스레드의 원칙**

- 하나의 스레드에서 동일한 그룹 내에 여러 개의 컨슈머를 생성할 수 없습니다.
- 하나의 컨슈머를 여러 스레드가 동시에 사용하는 것도 안전하지 않습니다.
- 따라서 **스레드당 하나의 컨슈머** 원칙을 반드시 지켜야 합니다.

<br>

**컨슈머 그룹 내에 여러 개의 컨슈머를 운용하고 싶다면**

1. 여러 개의 스레드를 생성하고,
2. 각각의 스레드에서 자체적인 컨슈머 인스턴스를 실행.
3. 이를 위해 **`ExecutorService`를 이용해 컨슈머 로직을 독립 객체로 감싸는 방식**이 일반적

<br>

**`poll()` 메서드 관련 주의사항 (Kafka Client API 변경 사항)**

- Kafka의 과거 버전에서는 `poll(long)` 메서드를 사용했지만, 현재는 **지원 중단(deprecated)**
- **신규 API는 `poll(Duration)`** 을 사용

- 동작 방식에 차이

| 구버전 (`poll(long)`) | 신버전 (`poll(Duration)`) |
|------------------------|-----------------------------|
| 타임아웃보다 오래 블로킹될 수 있음 | 타임아웃을 더 엄격히 준수함 |
| 메타데이터가 도착할 때까지 기다림 | 메타데이터를 기다리지 않음 |

<br>

**흔한 실수**

기존 코드에서 `poll(0)` 을 호출하여 **메타데이터를 가져오되 레코드는 읽지 않으려는 우회 방법**을 사용하던 경우,  
이를 `poll(Duration.ofMillis(0))` 으로 단순히 변경해도 **동일한 결과를 기대할 수 없다.**

<br>

**권장 대안**

- 메타데이터를 활용한 처리를 하려면 `rebalanceListener.onPartitionsAssigned()` 콜백 내에 로직을 구현하세요.
- 또는 다음과 같은 구조를 고려할 수 있습니다:

```text
[Consumer Thread]
  └─ 이벤트를 받아 큐에 넣음
       ↓
[Worker Threads]
  └─ 큐에서 이벤트를 꺼내 실제 처리 수행
