# 8.1 멱등적 프로듀서 (p206)

- 동일한 작업을 여러 번 실행해도 한 번 실행한 것과 결과가 같은 서비스를 '멱등적'이라고 한다.
  - 카프카에서 멱등성 의미 구조가 아닌 '최소 한 번' 의미 구조를 가지도록 하면 -> 프로듀서가 메시지 전송을 재시도할 때 한 번 이상 도착 할수도 있는 불확실성이 존재함.

- 고전적인 경우의 중복 메시지 전송
  1. 파티션 리더가 프로듀서로부터 레코드를 받아서 팔로워들에게 성공적으로 복제한다.
  2. 프로듀서에게 응답을 보재기 전, 파티션 리더가 있는 브로커에 크래시가 발생한다.
  3. 프로듀서 입장에서는 응답을 받지 못한 채 타임아웃이 발생하고, 메시지를 재전송한다.
  4. 재전송된 메시지가 새 리더에 온다. 하지만 이 메시지는 이미 저장되어 있다. (중복)

<br>

## 8.1.1 멱등적 프로듀서의 작동 원리

- 모든 메시지는 고유한 프로듀서 ID와 시퀀스 넘버를 가지게 된다.
  - 대상 토픽 및 파티션과 이 두 값을 합치면 각 메시지의 고유한 식별자가 된다.

- 각 브로커는 할당된 모든 파티션들에 쓰여진 마지막 5개 메시지들을 추적하기 위해 이 고유 식별자를 사용한다.
  - 파티션 별로 추적되어야 하는 시퀀스 넘버의 수를 제한하고 싶다면 프로듀서의 `max.in.flights.requests.per.connection` 설정값이 5 이하로 잡혀 있어야 한다. (기본값 : 5)

- 예전에 받은 적이 있는 메시지를 받으면 -> 적절한 에러를 발생해서 중복 메시지를 거부한다.

<br>

- 만약 브로커가 예상보다 높은 시퀀스 넘버를 받으면? -> 'out of order sequence number' 에러를 발생시킨다.
  - 에러가 발생한 뒤에도 프로듀서가 정상 작동시키면 메시지 유싱ㄹ이 있었음을 의미한다.
  - ex. 2번 메시지에서 -> 26번 메시지로 이동

<br>

작동이 실패한 경우, 멱등적 프로듀서가 어떻게 처리하는 지를 두 경우를 생각해보자.
- 프로듀서 재시작
- 브로커 장애

<br>

1. 프로듀서 재시작
   - 프로듀서 장애가 발생하면 -> 보통 새 프로듀서를 생성해서 장애가 난 프로듀서를 대체한다.
     - 멱등적 프로듀서 기능이 켜져 있으면 -> 브로커가 초기화 과정에서 프로듀서 ID를 생성 받는데, 이때 트랜잭션 기능이 켜져 있지 않으면 새로운 ID를 생성해준다.
     - 즉, 새로운 ID 이기 때문에 기존 프로듀서는 알지 못해, 메시지에 중복이 발생했음을 알아차리지 못한다.
2. 브로커 장애
   - 새 리더를 선출한다.
   - 리더는 새 메시지가 쓰여질 때마다 인-메모리 프로듀서 상태에 저장된 최근 5개의 시퀀스 넘버를 업데이트 하는데 -> 시퀀스 넘버가 있어 아무 이슈 없이 새로 쓰여진 메시지의 유효성 검증이 재개될 수 있다.
   - 예전 리더가 돌아온다면? -> 재시작 후에는 인-메모리 프로듀서 상태는 더 이상 메모리 안에 저장되어 있지 않다.
     - 단, 브로커는 종료되거나 새 세그먼트가 생성될 떄마다 프로듀서 상태에 대한 스냅샷을 파일 형태로 저장하기 떄문에, 복구를 위해 최신 상태를 일겅온다. -> 그리고 프로듀서 상태를 업데이트 함으로 써 최신 상태를 복구 시킨다.
    - 만약 브로커가 크래시 나서 최신 스냅샷이 업데이트되지 않는다면?
      - 각 파티션 최신 세그먼트의 메시지들도 사용하면서 복구 작업을 해서 새로운 스냅샷 파일을 생성한다.

<br>

## 8.1.2 멱등적 프로듀서의 한계

- 프로듀서 자체의 재시도 메커니즘에 의한 중복만을 방지할 뿐, 그 이상은 하지 않는다.
  - 동일한 메시지를 가지고 producer.send() 두 번 호출하는 건 -> 중복 메시지 가능하다.
  - 프로듀서들 중 두 개가 동일한 메시지 전송하려고 해도 중복을 잡아내지 못한다.

<br>

## 8.1.3 멱등적 프로듀서 사용법

- `enable.idempotence=true`를 추가하면 된다.
- 멱등적 프로듀서 켜져 있으면 다음과 같은 것들이 바뀐다.
  - 프로듀서 ID를 받아오기 위해 프로듀서 시동 과정에서 API 를 하나 더 호출한다.
  - 전송되는 각각의 레코드 배치에는 프로듀서 ID와 배치 내 첫 메시지의 시퀀스 넘버가 포함된다.
    - 각 메시지 배치에 96 비트를 추가한다. (오버헤드 x)
  - 브로커들은 모든 프로듀서 인스턴스에서 들어온 레코드 배치의 시퀀스 넘버를 검증해서 메시지 중복을 방지한다.
  - 장애가 발생해도, 각 파티션에 쓰여진 메시지들의 순서는 보장된다.
    - 2.5 버전 이후부터 레코드 배치에서 치명적인 에러가 발생하는 경우 -> 에러가 발생한 에러 포함해서 모든 전송중인 배치들은 거부될 것이다. (예외로 잡아서 건너뛸지, 재시도할지 결정 가능)
