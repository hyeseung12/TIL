# 8.2 트랜잭션 (p210)

- 카프카 스트림즈를 사용해서 개발된 애플리케이션에 정확성을 보장하기 위해 도입
- 스트림 처리 애플리케이션의 기본 패턴인 '읽기-처리-쓰기' 패턴에서 사용하도록 개발되었다.
- -> 이런 맥락으로 '정확히 한 번' 의미 구조를 보장할 수 있게 되었다.

## 8.2.1 트랜잭션 활용 사례

- 스트림 처리 애플리케이션, 금융 애플리케이션, 챗봇

## 8.2.2 트랜잭션이 해결하는 문제

1. 애플리케이션 크래시로 인한 재처리
   - 원본 클러스터로부터 메시지를 읽어서 처리한 뒤, 애플리케이션은 두 가지를 해야 한다.
     - 결과를 출력 토픽에 작성하기
     - 우리가 읽어 온 메시지의 오프셋을 커밋하기
   - 만약, 출력 토픽은 썼는데, 오프셋 커밋 전 크래시가 난 경우?
     - 애플리케이션에 의해 처리된 모든 레코드들은 다시 처리될 것이며 결과 역시 출력 토픽에 다시 쓰여져 중복이 발생할 수 있다.
2. 좀비 애플리케이션에 의해 발생하는 재처리
   - 애플리케이션이 카프카로부터 레코드 배치 읽어온 후 멈추거나, 카프카의 연결이 끊기면?
     - 위와 비슷한 상황으로 출력 토픽에 다시 결과를 쓰고, 작업을 계속한다.
   - 그 사이 멈춘 애플리케이션이 다시 작동하면 -> 마지막으로 읽어온 레코드를 처리하고 결과를 토픽에 또 처리할 것이다.
     - 다른 인스턴스는 이미 죽은 인스턴스로 판단해서 이 상태라는 걸 판단하기 전까지 계속할 수 있다.

<br>

## 8.2.3 트랜잭션은 어떻게 '정확히 한 번'을 보장하는가?

- 카프카 트랜잭션은 '원자적 다수 파티션 쓰기' 가 도입했다.
  - 결과를 출력 토픽에, 오프셋은 _consumer_offsets 토픽에 쓴다. -> 즉, 둘다 토픽에 적용함으로, 하나의 트랜잭션 안에서 수행할 수 있게 한다.

<br>

- 트랜잭션을 사용해서 원자적 다수 파티션 쓰기를 수행하려면?
  - 트랜잭션적 프로듀서를 사용한다.

    | 항목 | 일반 프로듀서 | 트랜잭션적 프로듀서 |
    |------|----------------|------------------|
    | 설정 | `enable.idempotence=true` | `transactional.id` 반드시 설정 |
    | 초기화 | 불필요 | `initTransactions()` 호출 |
    | PID (Producer ID) | 브로커가 매번 새로 부여 | `transactional.id`로 복원 가능 |
    | 재시작 시 PID 유지 | 새 PID 발급 | 동일 PID 재사용 |

  - `transactional.id`는 프로듀서를 재시작해도 동일 프로듀서로 식별되도록 해주는 ID입니다.
  - 브로커는 transactional.id <-> producer.id 매핑을 기억하고, 동일한 transactional.id 로 initTransactions() 호출 시 이전 producer.id를 재할당합니다.

<br>

- 애플리케이션의 좀비 인스턴스가 중복 프로듀서를 생성하거나 출력 스트림에 메시지를 쓰는 경우에 대한 문제
  - 해결 방법 : 에포크 기반 펜싱
    - 트랜잭션적 프로듀서가 initTransactions() 호출 시, 해당 transactional.id의 에포크 값 증가
    -  같은 transactional.id지만 낮은 에포크 값을 가진 프로듀서가 메시지 전송, 트랜잭션 커밋, 트랜잭션 중단 요청을 보내면 FencedProducer 에러 발생 → 거부
    - 따라서 오래된(좀비) 프로듀서는 출력 스트림에 쓰지 못하며, close()로 종료 필요
  - 추가 기능 (카프카 2.5 이후부터)
    - 트랜잭션 메타데이터에 컨슈머 그룹 메타데이터 추가 가능
    - 이를 펜싱에 활용하여, 좀비 인스턴스는 차단하면서 다른 트랜잭션 ID의 프로듀서들이 동일 파티션에 안전하게 기록 가능

<br>

- 트랜잭션은 주로 프로듀서 기능
  - 프로듀서에서 수행
    1. 트랜잭션 생성 및 시작
    2. 다수 파티션에 레코드 쓰기
    3. 처리된 레코드 오프셋 기록
    4. 트랜잭션 커밋 또는 중단
  - 트랜잭션 중단 상관없이, 레코드는 파티션에 기록된다.
  - 컨슈머에 올바른 격리 수준이 설정되어 있지 않을 경우, '정확히 한 번' 보장은 이루어지지 않는다.

<br>

- 쓰여진 메시지들을 읽어오는 방식 제어 (isolation.level)
  - read_committed:
    - 토픽들을 구독한뒤 consumer.poll()을 호출하면 -> 커밋된 트랜잭션과 트랜잭션에 속하지 않은 레코드만 읽음
      - 중단되거나 진행 중인 트랜잭션 레코드는 읽지 않음
    - 메시지의 읽기 순서를 보장 하기 위해 아직 진행 중인 트랜잭션이 처음으로 시작된 시점 Last Stable Offset(LSO) 이후에 쓰여진 메시지는 리터되지 않는다.
    - 트랜잭션이 프로듀서에 의해 커밋되거나 중단될 떄까지, 혹은 타임아웃으로 브로커가 트랜잭션을 중단시킬 때까지 보류된다.
      - 트랜잭션이 오래 열려 있으면 컨슈머 지연 발생 (transaction.timeout.ms 기본 15분)
  - read_uncommitted (default):
    - 진행 중/ 중단된 트랜잭션 포함 모든 레코드를 읽는다.

<br>

<img src="https://img1.daumcdn.net/thumb/R1280x0/?scode=mtistory2&fname=https%3A%2F%2Fblog.kakaocdn.net%2Fdna%2FkXqXX%2FbtsjImQAivY%2FAAAAAAAAAAAAAAAAAAAAAHvvTu_RdEbzpWI-l6sFd2Vfcjo1ec4G29dko6caDjBo%2Fimg.png%3Fcredential%3DyqXZFxpELC7KVnFOS48ylbz2pIh7yKj8%26expires%3D1761922799%26allow_ip%3D%26allow_referer%3D%26signature%3Du8LWBB8fM9b6GHXb42kNpC7mdOo%253D">

<br>

- read_committed 모드는 read_uncommitted 보다 약관 뒤에 있는 메시지를 읽는다.
- 스트림 처리 애플리케이션은 입력 토픽이 트랜잭션 없이 쓰여졌을 경우에도 '정확히 한 번' 출력을 보장한다.
- 원자적 다수 파티션 쓰기 기능은 -> 출력 레코드가 커밋되면 입력 오프셋도 커밋 -> 재처리 방지한다.

<br>

## 8.2.4 트랜잭션으로 해결할 수 없는 문제들

- 카프카 트랜잭션 기능을 사용할 때 자주 하는 두 가지 오해
  - ‘정확히 한 번’ 보장이 카프카 쓰기 외에도 적용된다고 생각
  - 컨슈머가 항상 전체 트랜잭션을 읽어 온다고 가정

<br>

1. 스트림 처리에 있어서의 부수 효과
   - 예: 이메일 발송, REST API 호출, 파일 쓰기 등
   - 트랜잭션 기능은 카프카에 쓰이는 레코드에만 적용됨
   - 외부 효과는 트랜잭션으로 취소 불가능 → 중복 수행 가능

2. 카프카 토픽에서 읽어서 데이터베이스에 쓰는 경우
   - 컨슈머가 카프카에서 읽고 데이터베이스에 쓰는 경우
   - 프로듀서 사용 안 함 → 카프카 트랜잭션으로 데이터베이스 작업을 보호할 수 없음
   - 해결: 오프셋을 데이터베이스에 저장하고 데이터와 함께 커밋
      - 트랜잭션은 데이터베이스가 제공하는 기능에 의존

3. 데이터베이스에서 일겅서, 카프카에 쓰고, 여기서 다시 다른 데이터베이스에 쓰는 경우
   - 한 애플리케이션에서 DB 읽기 → 카프카 쓰기 → 다른 DB 쓰기
   - 카프카 트랜잭션은 종단 보장(end-to-end guarantee) 제공 불가
   - 문제
     - 컨슈머의 read_committed 보장은 데이터베이스 트랜잭션과 맞물리지 않음
     - 트랜잭션 경계 알 수 없음 → 어느 메시지가 어느 트랜잭션에 속하는지 불명확

4. 한 클러스터에서 다른 클러스터로 데이터 복제
   - 카프카 클러스터 간 데이터 복제(MirrorMaker 2.0)
   - 레코드 단위 '정확히 한 번' 복제 가능 (KIP-656)
   - 한 트랜잭션의 원자성 보장 불가
     - 미러링 과정에서 트랜잭션 속성 손실
     - 관계형 DB로 복사 시에도 트랜잭션 정보 손실
     - 일부 토픽만 구독 시 전체 트랜잭션을 복사하지 못함

5. 발행/구독 패턴
   - read_committed 모드의 컨슈머는 중단된 트랜잭션 메시지 읽지 않음
   - 하지만 ‘정확히 한 번’ 처리 보장 불가
     - 오프셋 커밋 방식에 따라 메시지를 한 번 이상 처리할 수 있음
   - 카프카 트랜잭션 보장은 JMS 트랜잭션과 유사
     - 단, 모든 컨슈머가 read_committed 설정 필요
   - 메시지 발행 후 커밋 전에 다른 애플리케이션 응답 대기
     - 트랜잭션 커밋 전에는 메시지 수신 불가 → 데드락 발생 가능

<br>

## 8.2.5 트랜잭션 사용법

- 트랜잭션은 브로커 기능이며 카프카 프로토콜 일부인 만큼 여러 클라이언트들이 트랜잭션을 지원
- 권장 사용법 : 카프카 스트림즈에서 exactly_once 또는 exactly_once_beta로 잡아주면 된다.
  - 스트림즈가 내부적으로 트랜잭션 기능을 사용하기 때문에, 우리가 필요로 하는 보장을 제공해 준다.
- processing.guarantee = exactly_once 또는 exactly_once_beta

<BR>

## 8.2.6 트랜잭션 ID와 펜싱

- 핵심 조건 : 트랜잭션 ID가 애플리케이션 인스턴스가 재시작했을 때는 일관적으로 유지되고, 서로 다른 애플리케이션 인스턴스에 대해서는 서로 달라야 한다.

- 버전 2.5까지 펜싱을 유일하게 보장하는 건 -> 트랜잭션 ID를 파티션에 정적으로 대응하는 것 뿐이었ㄲ다.
  - 각 파티션이 항상 단 하나의 트랜잭션 ID에 의해 읽혀짐을 보장할 수 있었는데, 
    스레드에 할당되는 트랜잭션 ID는 랜덤하게 겨정되고, 동일한 파티션에 쓰기 작업을 할 때 언제나 동일한 트랜잭션 ID가 쓰인ㄹ 거라는 보장이 없었다.

- 버전 2.5에서 펜싱을 수행하는 두 번째 방법 -> 트랜잭션 ID와 컨슈머 그룹 메타데이터를 함께 사용하는 것을 도입했다.

<br>

## 8.2.7 트랜잭션의 작동 원리

- 기본적인 알고리즘은 '찬디-램포트 스냅샷(Chandy-Lamport snapshot)' 알고리즘의 영향을 받았다.
  - 이 알고리즘은 통신 채널로 '마커'라 불리는 컨트롤 메시지를 보내고, 마커의 도착을 기준으로 일관적인 상태를 결정한다.
  - 트랜잭션 커밋 또는 중단 표시 를 위해 마커 메시지를 사용한다.

<br>

- 일부 파티션에만 커밋 메시지가 쓰여진 상태에서 프로듀서가 크래시 나면?
  - 2단계 커밋과 트랜잭션 로그로 이 문제를 해결
    1. 현재 진행중인 트랜잭션이 존재함을 로그에 기록하고, 연관된 파티션들 함꼐 기록한다.
    2. 로그에 커밋 혹은 중단 시도를 기록한다.
    3. 모든 파티션에 트랜잭션 마커를 쓴다.
    4. 트랜잭션이 종료되었음을 로그에 쓴다.

- 트랜잭션 로그는 transaction_state 라는 이름의 내부 토픽을 사용한다.

<br>

- 알고리즘 작동 원리
1. **트랜잭션 초기화** (`initTransactions()`)
   - 프로듀서가 자신이 **트랜잭션 프로듀서**임을 브로커에 등록
   - 트랜잭션 코디네이터 역할 브로커로 요청 전송
   - **트랜잭션 로그 파티션 리더**가 해당 트랜잭션 ID를 관리
   - 새 트랜잭션 ID 등록 또는 기존 ID의 **에포크(epoch) 증가**

2. **트랜잭션 시작** (`beginTransaction()`)
   - 프로토콜 레벨은 아니며, 프로듀서에게 **현재 트랜잭션 진행 중**임을 표시

3. **레코드 쓰기**
   - 트랜잭션 내에서 여러 파티션에 메시지 전송

4. **오프셋 커밋 준비**
   - 트랜잭션에서 처리한 레코드들의 **오프셋 준비**
   - `sendOffsetsToTransaction()` 호출 시, **오프셋 + 컨슈머 그룹 ID**를 트랜잭션 코디네이터에 전달

5. **트랜잭션 종료**
   - `commitTransaction()` → 트랜잭션 커밋 요청(EndTxn)
   - `abortTransaction()` → 트랜잭션 중단 요청(EndTxn)

6. **트랜잭션 타임아웃 처리**
   - `transaction.timeout.ms` 시간 내에 커밋/중단되지 않으면 **자동으로 트랜잭션 중단**
